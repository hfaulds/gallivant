# No `nil`

`nil` causes a large share of Go runtime panics. Gallivant rejects `nil` in
your code by default and pushes you towards `Option` and `Result` instead.
Existing Go code can opt out with one line in go.mod, so it still builds.

## The default

Every package of a main module is compiled with `-nonil`. In those packages:

- The predeclared identifier `nil` is an error: `use of nil in nonil module;
  use Option, Result or a zero value instead`.
- So you can't compare a value with `nil`. Use `match` or `Option` instead of
  `if p != nil`.
- `Err(nil)` is rejected.
- Files generated by cgo (`_cgo_*.go`) are exempt, since cgo's generated
  code uses `nil` freely.

Values of nilable types can still *be* nil. A `*T` field's zero value is nil,
and code you call can hand you nil. What `nonil` removes is producing nil and
comparing against it in your own code. Dereferencing a zero-value pointer
still panics exactly as in Go.

Packages that are never compiled with `-nonil`:

- The standard library and `cmd`, and anything else in `GOROOT`.
- Dependency modules, whatever their go.mod says. Only main modules are
  checked, including every module of a workspace. The ecosystem's existing
  Go libraries keep working, and since `-nonil` only ever rejects code,
  exempting them does not weaken the check on your own code.

## Opting out: `nonil false`

A module written before Gallivant, or one that has not been converted yet,
opts out in its go.mod:

```
module example.com/legacy

go 1.27
nonil false
```

`nonil` and `nonil true` state the default explicitly. Any other argument is
a go.mod error.

Code with no go.mod, either in GOPATH mode or built as `go run file.go`
outside a module, is also compiled with `-nonil`. It opts out on the command
line:

```
go run -gcflags=-nonil=false file.go
```

cmd/go puts its `-nonil` before any user `-gcflags`, so the user setting
wins. Put it in `GOFLAGS` (`GOFLAGS=-gcflags=all=-nonil=false`) to opt out a
whole GOPATH workspace.

## Working with the standard library

Many standard-library functions return `(T, error)` or use a nil pointer to
mean "absent". Two small standard-library packages bridge them:

```go
result.Wrap(strconv.Atoi(s))        // Result[int]: Ok(v) if err == nil, else Err(err)
result.Unwrap(r)                    // (T, error), the reverse
result.Must, result.Or, result.Map, result.Then, result.ToOption
option.FromPtr(p)                   // Some(*p) if p != nil, else None
option.FromOK(v, ok)                // from v, ok := m[k]
option.Or, option.OrZero, option.Must, option.Map, option.IsSome, option.IsNone
```

They are ordinary Go packages (`src/option`, `src/result`) and can grow
without touching the compiler.

## Status

Implemented: nonil by default for main modules and code outside modules, the
`nonil [true|false]` go.mod directive, `go list -m -json` reports
`"NoNil": true` for main modules compiled with `-nonil`, cmd/go passes
`-nonil` (and includes it in the build cache key), and the type checker
reports `use of nil in nonil module`.

Future work: a `go vet` check that flags exported functions returning
nilable types where an `Option` or `Result` would be clearer.
